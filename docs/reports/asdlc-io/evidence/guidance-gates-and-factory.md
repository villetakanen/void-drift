## Page propositions

**G-G01 — Getting Started with Agentic SDLC: Setup Guide** (`https://asdlc.io/getting-started/`; no displayed status/update metadata). Under “The Five-Minute Version” it calls the Spec the permanent source of truth, puts specs before code, separates Spec state from PBI delta, and presents three gate layers: deterministic, probabilistic, and human. “The Gate Hierarchy” orders Quality → Review → Acceptance before Merge. It also says the framework is production-oriented and likely overkill for a weekend project. This concise onboarding page uses “primary source code” phrasing for the Spec, which needs the qualification made by the current “The Spec” pattern below.

**G-G02 — The Spec: Living Specifications for Agentic Development** (`/patterns/the-spec/`; Live; last updated 2026-10-05). “Definition” and “Spec-anchored” identify the durable feature spec as source of architectural intent and functional contracts, evolving with implementation. “Anatomy” separates Blueprint constraints from a Contract of observable DoD, invariants, and behavioral scenarios. “Specs as Living Hypotheses” requires refinement as implementation reveals unknowns; the spec is not frozen waterfall. Crucial boundary under the three maturity levels / anti-pattern “Spec-as-Source”: the ASDLC target is spec-anchored; it explicitly rejects specs as the sole source file replacing deterministic runtime code. Accordingly, the Getting Started “primary source code” metaphor should be read as authority for intent, not literal executable/source authority.

**G-G03 — Spec-Driven Development** (`/concepts/spec-driven-development/`; Live; 2026-05-26) and **Living Specs: Creating and Maintaining Specifications That Evolve With Your Code** (`/practices/living-specs/`; Live; 2026-10-05). “Determinism Over Vibes” assigns mechanical orchestration to code and flexible implementation to LLMs. “Levels of SDD Adoption” again selects spec-anchored, not spec-as-source. Living Specs “When to Create a Spec” explicitly exempts routine bug fixes, config changes, dependency bumps, or one-off tasks when existing intent already covers them; a spec that adds no information is maintenance burden. “The Same-Commit Rule” and “The Refinement Cycle” call for updating behavior contracts alongside behavior and expect discovery during implementation. The guide also favors focused, domain-sized specs and says its template is adaptable: omit sections that add no information. Tension is mostly resolved internally: Getting Started’s “Write specs before code. No spec, no build” is broad onboarding shorthand; the detailed living-spec practice gives proportional scope and no-new-spec cases.

**G-G04 — Agent Constitution** (`/patterns/agent-constitution/`; Live; 2026-02-18). Under “Taxonomy: Steering vs. Deterministic Constraints,” constitutions steer judgment probabilistically; toolchain and runtime/orchestration enforce hard constraints. Its decision rule says put mechanically enforceable rules in tooling, not duplicate them as agent instructions. The page calls negative constraints least reliable and says critical ones need deterministic backing. Though its “Anatomy” includes “Boundaries (Negative Constraints),” the page explicitly labels them soft steering and less reliable; this is a documented tension, not a claim that prose itself blocks action.

**G-G05 — Context Gates** (`/patterns/context-gates/`; Experimental; 2026-07-15). “Dual-Mandate Checkpoint Architecture” distinguishes input filtering (handoffs and within-session relevance) from output validation. “Output Gates” defines Quality Gates as binary/toolchain checks; Review Gates as probabilistic, adversarial Critic review; Acceptance Gates as human strategic/product judgment. A separate “Workflow Enforcement (Denial Gates)” describes runtime blocking. The page recognizes that AI tests can miss semantic violations, but also warns “Review Gate Evolution and Risks”: judges can share blind spots or drift, and therefore need frozen independent anchors plus deterministic quality gates. Experimental maturity matters: Getting Started presents the three-tier hierarchy as core, while this detailed architectural treatment is labeled experimental.

**G-G06 — Adversarial Code Review** (`/patterns/adversarial-code-review/`; Live; 2026-10-05) and **Adversarial Code Review** (`/practices/adversarial-code-review/`; Live; 2026-05-20). The pattern’s “Separated Roles” and “Context Swap” recommend a distinct/fresh Critic session comparing spec and diff, returning violations or PASS before human review. Its own “Implementation Constraints” says the pattern is manual, large diffs exceed context, vague specs yield vague critiques, negation is a weak point, and model review capability must be validated on representative examples. The practice adds “Skip this practice when” clauses for trivial docs/refactors and exploratory prototypes without specs. Thus these pages do not establish probabilistic review as universally required or reliable; they position it as a spec-dependent additional lens, not a deterministic check.

**G-G07 — Constitutional Review** (`/patterns/constitutional-review/`; Live; 2026-01-31) and **Constitutional Review Implementation** (`/practices/constitutional-review-implementation/`; Experimental; 2026-01-08). “Dual-Contract Validation” distinguishes functional spec compliance from architectural constitution compliance, both reviewed by a Critic. The practice says skip when there is no constitution, no architectural constraints, or overhead exceeds benefit for a very small project. It expressly notes false positives and exceptions; human acceptance remains essential. The pattern includes a production case narrative in which a performance anti-pattern passes tests and functional checks but is found by review; that is the page’s case claim, not evidence independently checked here.

**G-G08 — Workflow as Code** (`/practices/workflow-as-code/`; Experimental; 2026-10-01). “When to Use” targets repetitive/high-reliability workflows and explicitly says to skip exploratory, simple linear, ad hoc, or low-stakes work. “Process” separates mechanical actions (commands, parsing, branches, file/API operations) into typed deterministic code from review/summarization/implementation into probabilistic calls; hooks can hard-block bypasses. The example orchestrator sends an AI review result to deterministic commit/PR steps, while the page’s rules say use it only when the probabilistic verdict is structured. In combination with the L3 human approval pages, this leaves an implementation detail to clarify: a critic PASS must not be mistaken for strategic human acceptance or permission to publish.

**G-G09 — Feature Assembly** (`/practices/feature-assembly/`; Draft; 2026-01-09). “Assembly Pipeline” presents PBI + Spec → code → gates → merge, and “Phase 3: Quality Gates” specifies deterministic required, Critic review recommended, human acceptance required. “Phase 4” also says all gates pass before merge, with critic PASS conditional “if using adversarial review.” It says spec is read-only during assembly unless explicit refinement is required, while requiring changed contracts to be updated alongside code. The practice later says “Never Skip Gates,” proposes automatic CI gates, and gives target pass-rate/coverage/cycle metrics; these are draft prescriptions, not a single coherent universal contract. Read together with the explicit skip/proportionality conditions in G-G03, G-G06, G-G07 and G-G08, “never skip” is best scoped to the applicable required quality gates, while Review Gate applicability is conditional and human acceptance is a separate L3 decision.

**G-G10 — Agentic SDLC: The Software Factory Framework** (`/concepts/agentic-sdlc/`; Live; 2026-05-20) and **AI Software Factory** (`/concepts/ai-software-factory/`; Experimental; 2026-03-09). The former frames L3 Conditional Autonomy: agents execute logistics and verification, humans define intent/architecture and govern; it separates the software-building loop from meta-optimization of agents. The latter contrasts a human-governed “Safe Factory” (L3) with “Dark Factory” L4 and highlights governance/liability concerns when human review is eliminated. The two pages make factory and autonomy claims with different maturity labels; they do not make all autonomous delivery equally recommended.

**G-G11 — Levels of Autonomy** (`/concepts/levels-of-autonomy/`; Live; 2026-06-30). “Autonomy Scale Matrix” defines autonomy by operational independence, execution boundaries, and oversight, not model capability. L3 is multi-file orchestration with automated validation followed by human change-owner review; L4 shifts to post-hoc audit. “The Level 3 Production Ceiling” argues for a human gate and warns that self-changing evaluators press beyond L3. It is a taxonomy/position, not an objective score for a repository; the scale’s car analogy should not replace concrete authority descriptions.

**G-G12 — Provenance** (`/concepts/provenance/`; Live; 2026-10-08). “Definition” asks who intended an artifact, why, and how verified. “Provenance and Intent Debt” explicitly says traceable commits/gates alone do not preserve rationale, trade-offs, or rejected alternatives; Specs, ADRs, and Constitutions carry intent. Provenance is therefore not equivalent to passing checks or retaining only a run report.

**G-G13 — Harness Engineering** (`/concepts/harness-engineering/`; Experimental; 2026-10-08). “Guides vs. Sensors” distinguishes pre-action instructions/schemas from post-action tests, compilers, and telemetry. “On the Loop vs. In the Loop” frames humans as designing and improving the execution substrate as well as governing work. Its proposed layers include interfaces/context, execution/memory/sandbox mechanisms, and multi-agent coordination. This is a developing concept page; its research and operational examples are not assessed here.

**G-G14 — Theory of LLM Constraints** (`/concepts/theory-of-llm-constraints/`; Experimental; 2026-10-01) and **Feedback Loop Compression** (`/concepts/feedback-loop-compression/`; Experimental; 2026-10-01). The former argues that generation speed can shift constraints toward verification and calls for minimal baseline checks plus additional risk-earned gates, rather than ritual scaffolding. It notes that cited evidence measures different outcomes and none directly measures a moved queue; its claims motivate diagnosis, not a transferable effect size. The latter argues that faster observation/orientation can improve human decisions, but names “Shipping Blind” and “Speed Over Understanding” as anti-patterns and says compressed loops do not remove human oversight. These caveats temper the factory narrative: neither faster iteration nor more gates alone is evidence of better outcomes.

**G-G15 — Agent Optimization Loop** (`/patterns/agent-optimization-loop/`; Experimental; 2026-03-18). “Offline vs Online Evolution” distinguishes human-reviewed, version-controlled offline changes from experimental online context adaptation. “Controlled Evaluator Evolution” freezes evaluators during epochs and permits promotion only at boundaries against independent frozen anchors. The page says agent-proposed harness changes remain proposals and require deterministic validation or human architectural review. It is a meta-lifecycle for improving agents, not a required feature-delivery gate.
