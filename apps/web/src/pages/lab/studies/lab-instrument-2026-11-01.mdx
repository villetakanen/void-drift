## Question

What does a single shared instrument look like that every study and the Lab use to compare paths, engines and hulls on the same measurements?

A study that varies engine thrust and a study that varies hull mass both end up drawing a path, a speed curve and a few figures. Each builds that drawing with its own axes, units and input program, so the two results cannot be laid side by side, and neither can be checked in the Lab. The work of measuring is repeated and the comparison is lost.

The Lab instrument is one shared element that owns the measuring. A study hands it vehicle configurations and path sources; the instrument decides the views, scales, units, input program and controls. Paths are calculated, not flown, and drawn statically. The same element fills the container in the Lab and, in a study, takes the full column width and snaps to the centre of the reading flow. All controls sit in one collapsible pane that slides over the views.

**The screen.** Two columns of equal width inside an even margin, with no header and no footer. The plan view takes the left column; the time-based diagrams take the right.

**The control pane.**

- Controls live where they act. Tools for reading the diagrams (time, scale, panning, showing a vehicle) sit on the diagrams themselves.
- The pane holds only the values under investigation: the settings a study varies and the document they are copied from. It is placed on the instrument's container, not drawn inside the scaled screen: anchored to the right edge, the container's full height, at a normal readable size.
- It is either visible or hidden, with no animation. When visible it sits over the screen; nothing behind it moves, resizes or reflows.
- It always starts hidden. Hidden, only a menu button in the container's top-right corner remains; visible, the pane's own close button takes that corner. Escape also closes it.
- Content taller than the screen scrolls inside the pane. Targets stay touch-sized.

**A configuration that travels.** The instrument is only used if handing it work is easier than building a chart. That hand-over is a configuration: a small document an agent writes, the instrument draws, and the designer adjusts on screen. If a plasma study wants faster acceleration, the designer changes that one value in the pane, compares it with the stock ship, and copies the resulting document back to the agent, or the agent reads it from the page, as the decided values. Nothing in the document is mandatory; it names only what differs.

The open questions were about that document: what a vehicle in it is, which parameters can change, which ships can be used, and how many vehicles one screen can hold. The game already described ships as loadouts (a chassis with parts in fixed slots) and parts as parameter sets (mass, thrust, speed limit, response), which was a likely starting vocabulary. The default path scale, the slider as a design-system component and device readability checks sat outside this cycle.

## 02.1 Anatomy: three views, one readout, one pane

One fixed 16:10 screen holds a plan view of every path, three traces on a shared time axis with the input program beneath them, and a readout table. The table joins the moment (values at the slider time), the whole run (peak speed, time to 200 u/s, distance) and the configuration a study supplied, so an engine or hull comparison reads from the same calculation as the paths.

The example used four vehicles from two imagined studies, calculated with the free-rotation bench (2 aft + 2 side) on the shared 14-second input. The configuration columns showed only the two settings that bench varies; real engine and hull properties were not connected. Samples are 1/60 s apart. The screen scales with its container; it had not been checked on an iPad.

## 02.2 A vehicle is a loadout plus what differs

Each vehicle in the configuration is a game loadout (a chassis with parts in its fixed slots, the same document the ship builder saves) plus an optional list of changes. Changes are grouped by engine family and name only the values that differ from the game, so a document that lists nothing describes ships exactly as they fly today.

```json
{
  "label": "Plasma aft, more thrust",
  "loadout": { "version": 2, "chassis": "balanced", "side": "ion",
               "stabilizers": true, "hull": [null, null],
               "aft": ["plasma", "plasma"] },
  "changes": { "plasma": { "thrust": 46000 } }
}
```

Changes belong to one vehicle, so the stock part and a changed one can be compared side by side. Because they are keyed by engine family, the values that should become the part's new definition can be read straight from the document.

## 02.3 Reading tools on the diagrams, values in the pane

Each kind of control sits where it acts. Time is scrubbed on the traces themselves (drag across them, or use the slider beneath); the plan view carries its own scale buttons; a vehicle is hidden or shown from its row in the readout. The pane opens to only the values under investigation and the document, so what it contains is exactly what gets copied back.

In a study the instrument takes the full width and height of the window and snaps into place as it is scrolled to. The working example started from a three-vehicle document: a Fighter with ion aft engines, the same with plasma, and plasma with more thrust. Changing a value in the pane moved the paths and readout.

![The three-vehicle configuration with the values pane open on the right](/studies/lab-instrument-2026-11-01/023-configuration-pane-open.jpg)

Paths are calculated with the game's own engine function on the shared 14-second input. Not included: gravity, power limits, and changes to part mass or chassis values, which that function does not take per vehicle. Ion values are shared by light and heavy ion and the stabilisers; the turn cap applies to every ship. Out-of-range values are refused rather than drawn.

<h2 id="toggle">02.4 A two-option toggle</h2>

The plan view's scale buttons choose one of two options, and the design system had no control for that. The toggle is one button: its outer edge has the shared cut corners, and inside it is split straight down the middle into two equal halves. The selected half is filled like the shared filled button, so the selection reads with the same weight as a primary action.

Two treatments of the unselected half were compared: inside a ghost button's lime border, or with no border as a faint fill. The faint fill without a border was chosen. It keeps the control quiet beside the diagrams and leaves lime for the selection alone.

The resting state worked; the hover state did not, because darkening the faint fill made the half sink into the surface instead of answering the pointer. Four hover treatments were compared: A, the fill brightens; B, the half previews a ghost button; C, the shared selected-indicator bar appears along its bottom edge; D, the lift is kept but the semi-transparent white becomes semi-transparent lime, so hover borrows the brand colour at low strength while the selection keeps it at full.

![Four hover treatments of the unselected half of the two-option toggle](/studies/lab-instrument-2026-11-01/024-toggle-hover-comparison.jpg)

*02.4, reconstruction from current code, captured 24 November 2026. Each treatment shown at rest and in the hover state drawn without a pointer, above the shared Filled and Ghost buttons for reference. **Accepted: D, brand tint.** One control with the shared cut corners outside and a straight split inside. The selected half is filled lime; the unselected half is a faint white fill with a white label; on hover that fill turns to the same strength of lime (28%). The plan view's scale toggle in 02.7 uses it. It was not in the shared button styles when the study was written. Hover exists only with a mouse or trackpad; on the iPad a touch selects directly, so the resting and selected states carry the control there. Toggles with more than two options and on/off toggles were outside this comparison.

<h2 id="slider">02.5 An on-brand slider</h2>

The instrument needs sliders in two places: time on the diagrams, and the values under investigation in the pane. Sliders elsewhere in the Lab were the browser's own, tinted lime, with a label and the value beside it. They work, but nothing about them belongs to the brand.

- A first round drew the slider in the brand's shapes: a cut-corner thumb on a tall rail, a filled gauge, and a ruler with a marker. Each lost what makes a slider recognisable, a thin track and a handle to drag, so it was set aside.
- A second round kept that anatomy, with a lime fill and either a round or a cut-corner handle. The round handle was chosen, but lime on the fill, the value and the handle together was too much brand colour for a control that sits beside the diagrams.
- A third round kept lime on the knob alone, with a grey fill and a white value. It was calm but lifeless: the slider stopped looking like part of the instrument.
- The fourth round used lime sparingly: the fill up to the value and the knob, and nothing else. The label and value stay neutral, and the unfilled track takes the accepted faint lime tint under a pointer. Both variants keep the native input underneath, so arrow keys, touch and screen readers behave as before, with a 44px touch height. A has a 4px fill and a solid knob; B has a 2px fill and a lime ring.

![Slider variants A (solid knob) and B (ring knob) with a hover state previewed](/studies/lab-instrument-2026-11-01/025-slider-comparison.jpg)

## 02.6 Three burns, and how the input reads

The instrument owns a small set of input programs, all 14 seconds long; a study picks one and never writes its own.

- **Course:** the original mixed program: burns, coasts, single-engine turns and restarts.
- **Turn:** 6 s on both engines, 2 s left only, 1 s coast, then both engines to the end. Acceleration, one committed turn, and the burn out of it.
- **Weave:** both, left, right, repeating; each round's steps are 0.3 s longer than the last (0.3, 0.6, 0.9 s and on) until 14 s, so response is tested from the quickest taps to held inputs.

Picking a burn is a three-way choice, so the switcher is the accepted toggle split into three equal parts, labelled B1, B2 and B3. Two codings for the input strip were compared: one colour per input, or lime lanes where the upper lane is the left engine and the lower the right. The lanes were chosen; they read well and add no hues beside the vehicles' trace colours.

The switcher sits on the strip it chooses, just left of the lanes, so the lanes stay on the traces' time axis. The burn is part of the configuration document, so a switched burn is copied back with the values. With the strip, the toggles and the slider all in lime, the instrument overused the brand colour, so five tones for the lit lanes were compared, from the current lime to grey: A, lime; B, soft lime (lime at 45%); C, white (the text colour); D, soft white (white at 70%); E, grey (the dim text colour).

## 02.8 The path tool's edge and material

Fixed for the path tool, not open in this step:

- Its plot is square, 1:1.
- Its width is one 50% column of the iPad screen, with sensible padding.
- It has the scale switch.
- It shows its numbers: the area shown, the grid and the scale.
- It shows the area of space in relation to the path.

Within those, the step asked how the plot separates from what is around it. A first round compared a framed panel with no frame; this round varied what the edge is made of. The design system had no elevation, so two study-local steps were tried. Mixing the app's ivory white into the background pulled them towards a neutral grey, and keeping only the background's faint chroma left them close to neutral, so they keep its hue (290) and raise chroma with lightness: elevation 1 is lch(5.5% 10 290), elevation 2 lch(11% 15 290). The example area was elevation 1; the plot was elevation 2.

Of five edges tried (white or brand border; white, brand or black shadow), the black shadow was accepted: the plot casts a soft shadow downwards, 8px down with a 24px blur.

Lightness steps alone read as slightly lighter blue-black, not as anything in a space instrument. A switch above the path tool then changed the material of both levels, all on the background's hue of 290:

- **Tinted void:** the lch steps above, kept as the reference.
- **Lit plate:** machined panels lit from the upper left, as the engine studies light their parts: a soft diagonal gradient and a thin highlight on each level's upper-left edge.
- **Glass over space:** a faint starfield behind tinted glass; the plot is denser glass that blurs the stars behind it.
- **Instrument display:** a flat console holding a display with faint scanlines on the 4px rhythm and a darkened edge.

## 02.10 The time graphs: the basics

Speed, acceleration and turn acceleration are one graph component used three times; they differ only in name, unit and range. They share the path tool's display material and shadow, but they are graphs, so they need measurements and every label outside the data:

- A value axis on the instrument's fixed scale, never fitted: about five ticks with values and gridlines, a stronger zero line where the range crosses zero.
- A time axis, 0–14 s with a gridline and a label every second, the same on every graph: the component is one complete graph, shown three times.
- A title row above the plot: the measure and its unit on the left, and on the right the time and each vehicle's value at the cursor, in its colour. A warning appears there if a value exceeds the fixed scale.
- The time cursor: a vertical line with a dot on each trace.
- Margins on the 4px grid: 28px for the title row, 52px for the value labels, 24px for the seconds. Each graph is 176px tall, so three with 16px gaps leave 112px of the path tool's 672px for the lanes and slider.

## 02.11 The composed view

The path tool and the time graph put together on the instrument's screen. The screen is the console, elevation 1. The left column holds the path tool at its square size with the burn row under it, as accepted in 02.6: the compact B1–B3 switcher, then the selected burn's lanes in soft white. The right column holds the graph three times, 208px each with 24px between them, with the time slider under it. Both rows are the full column width and 44px tall, 24px below their block, so the two columns end level; the slider's knob runs along the graphs' time axis. Below both columns, one row across the screen names the vehicles: a short line in each one's colour, then its label, for the two to six vehicles a configuration holds. The pane is not shown. The screen fills the window and snaps into place.

**Decided here:** every graph scales its value axis to fit the data, rounded out to a nice value, and a measure that can go negative stays symmetric about zero. This replaces the fixed scales of 02.10: nothing is clipped, and values are compared by reading the axis rather than the height of a line. The path tool keeps its own switch between fitting all paths and the default scale.

## 03 Readiness: what ships as v1

The accepted design is the composed view of 02.11 with the pane on top: the path tool and its burn row in the left column, the time graph three times and the time slider in the right, the legend across both, all on the console and display materials. The pane overlay was specified but not yet drawn: elevation 3 on the same progression as the two below it (lightness up 5.5 and chroma up 5 per step, so lch(16.5% 20 290)), 45% of the screen wide, and an 11% opaque backdrop over the rest. What the pane holds is filled in by the agent for each study.

**Ready to reuse.**

- **Calculation:** paths come from the game's own engine function, with each vehicle's part and ion values passed in, so a study's changes never touch the game's definitions.
- **Configuration document:** one validated schema: vehicles as loadouts plus sparse changes, and the burn. It already round-tripped through Copy and Load in the 02.3 pane.
- **Burns:** B1–B3 as data, each exactly 14 seconds.
- **Diagrams and controls:** the path tool, the time graph, the burn lanes, the two- and three-part toggle and the ring slider, each a separate component in its accepted form, plus the shared display material.
- **Pane behaviour:** shown or hidden from a corner button, Escape and focus return, as specified in 01 and built in 02.3.

**Required before v1 ships.**

1. One component from one document. The composed view was wired to the study's example vehicles; it has to take a configuration document, validate it, and derive the paths, graphs, burn and legend from it.
2. The pane overlay, drawn to the specification above, with a slot the host fills. Its default content is the existing value editor and the document's Copy and Load, set in the accepted controls.
3. Where it lives: the components move out of the study folder into the Lab's own components; the frozen copies stay with the study as its record.
4. A Lab page and a study embed. The Lab page fills its container; in a study the instrument takes the full window and snaps into place.
5. How agents call it: a specification of the contract and one rule in the design-study skill, that motion, engine and hull comparisons use this instrument and its configuration document rather than new charts.
6. Design-system pages: the new components join the shared design system, each with a Lab reference page as the buttons have. The toggle and the ring slider go with the inputs, beside the buttons; the path tool and the time graph on a Graphs page; the burn row, the legend and the pane overlay on a Lab components page; the elevation steps and the console and display materials with the foundations.
7. Tests: unit tests for the burns, the schema and the calculation; one browser test of the composed view, the burn switch, the slider and the pane.

**Provisional, not blocking.** The path tool's default scale (0.2 px/u) had not been tuned. Time moves in 1/60 s samples.

**Risks and limits.**

- Fidelity: gravity, power limits, and changes to part mass or chassis values are not in the calculation. A difference shown here may not exist in flight; the specification has to say so.
- Comparison across studies: with every graph scaled to its data, two studies are compared by reading their axes, not by laying the lines over each other.
- Readability: the whole screen scales with the window, so text gets small on small windows. Nothing had been checked on a physical iPad.
- Elevation 3: its value is an assumed continuation of the progression and had not been seen.

## 04 Integration plan

Each step was to leave the instrument working and be reviewable on its own. This was a plan; building it needed a separate go-ahead. The order:

1. Data first: move the configuration schema, the burns and the calculation into one Lab module, unchanged, with unit tests (each burn is 14 s, the schema accepts the 02.7 document and rejects a broken loadout, the calculation is deterministic).
2. The component, built from the 02.11 view and taking a configuration document; check it renders the 02.7 document exactly as 02.11 does.
3. The pane, with a slot and the default value editor and Copy and Load. Review point: the designer judges elevation 3 and the backdrop in place.
4. Design-system promotion and the reference pages listed under 03: the toggle (two and three parts, with the lime-tint hover) and the ring slider become shared input styles; the elevation steps and the console and display materials become foundation tokens. Review point: the designer checks each page against its accepted section.
5. The Lab page, with a starting document and Load. Review point: the designer uses it for one real comparison.
6. The study embed and the contract: the full-window embed, the specification (the document, the burns, the views and the decisions above, with targets kept apart from what is built), the rule in the design-study skill, and the new inputs, graphs and foundations in the design guide and the design-system specification.
7. Verification: lint, type and Astro checks, the unit tests, a browser test of the view, burn switch, slider and pane, a render check of every new reference page, and a human review on the iPad for readability. Mark the study integrated only after these pass and the review is recorded.

Follow-ups, outside v1: add part mass, chassis values, gravity and power limits to the calculation; more burns, if studies need them; tune the path tool's default scale.
