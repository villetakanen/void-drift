**Accepted by the designer, revision 9, 28 October 2026.** The designer approved
the study and authorized integration: shared tokens, buttons, groups, the
canonical Lab and the existing application screens.

## Situations before styling

Buttons serve three situations:

- **Game-state navigation:** startup, pause, continue, setup and mode selection
  are screens or modal states of the game. Their buttons move the player between
  states. Start game and Continue can be the primary action, so navigation is
  not always secondary.
- **Application state actions:** players save ship designs, save settings,
  revert edits or reset forms. These actions change application data. Saving
  and resetting need clear outcomes and availability states.
- **Lab tools:** developer tools use the application’s button styling and
  hierarchy. Controls are grouped by purpose within their context; tooling has
  no separate visual system.

Hierarchy follows the player’s immediate goal. Whether an action navigates or
saves does not decide it. HTML semantics follow behavior: links for URL
destinations, buttons for in-app state transitions and commands.

## Hierarchy and states

- One primary, secondary and destructive hierarchy serves game screens, player
  tools, settings and the Lab. The primary button advances the main goal: Start
  game, Continue game, Save settings or Save blueprint, depending on context.
- Filled lime marks the main goal, whether it navigates or saves. Lime-outline
  ghost buttons support it. Red marks an action with consequences; it does not
  mark priority.
- Selected is a persistent state (Play/Pause); pressed is momentary. Hover and
  keyboard focus look different. Focus uses an inset outline so the button shape
  cannot clip it.
- All targets are at least 44px high. Busy and unavailable controls cannot run
  again; busy uses the disabled state, with no separate loading animation.
- Buttons use the application’s existing angled corners and colors (revision 3).

## Containers

Buttons sit in one of two containers (revision 4):

- **Vertical button group:** equal-width buttons stacked on a transparent
  background, as in startup and pause screens.
- **Anchored action strip:** a solid background, supporting actions on the left
  and the main action anchored on the right.

Navigation buttons form a group with one main path and supporting destinations.
Data actions are arranged around a fixed save position: Save stays in place
through idle, busy and saved states, and revert/reset is placed apart from it by
consequence. Lab tools follow the same rules: transport controls sit together
and reset is placed apart.

**Spacing:** every button container has padding on all four sides equal to its
button gap, even when transparent. Both containers use 8px (revision 6).
Anchored groups may have more space between them; their minimum gap and outer
padding remain 8px.

Below a 580px container width, a strip stacks its groups in one column and keeps
its background and 8px padding; it does not become a transparent navigation
group. The vertical group stays transparent.

## Tokens

Before promotion the designer asked for a complete token inventory (revision 7).
In revision 8 the designer established `--_name` for private component tokens:
declared on the owning component rather than `:root`, for local aliases, derived
values and implementation details. Shared visual decisions remain public tokens.
For example, `--_group-spacing: var(--spacing-sm)` supplies both padding and gap.
The prefix records which component owns a token; CSS does not enforce privacy.

The promotion on 28 October 2026 implemented:

- Public foundations: control height, control font size/weight, border width,
  focus color/width/inset, disabled opacity, hover brightness, selected
  indicator width, and motion duration/easing.
- Private composition: button padding/radius/cut/inset/line-height/transition
  aliases; group spacing and vertical maximum width. Existing public button
  aliases are retained for compatibility.
- Shared behavior: inset focus, disabled hover suppression, selected indicator,
  44px minimum link-button target, and reduced-motion transitions. Busy behavior
  remains the caller’s responsibility.
- The 580px container threshold stays a documented private layout rule. Dialog
  dimensions, demonstration delays, preview widths and feedback framing stay
  outside the button contract.

## Ruled out

- **A generic discard confirmation as the lead example** (revision 2): the
  designer corrected that “dialog buttons” primarily navigate the game’s
  startup, pause, setup and mode states. Confirmation stayed only as a
  supporting example of an action with consequences.
- **An equal-width strip** (revision 4): replaced by the two containers.
- **16px vertical spacing** (revision 6): the designer found it too loose;
  vertical padding and gaps were reduced together to 8px.
- **Study-only 120px/172px minimum widths:** removed at promotion. Horizontal
  buttons size to content; vertical buttons fill their shared container. No
  generic width tokens were added.

## Uncertain

- Action order remained under review. Action order and reset confirmation are
  set per workflow and do not block the shared baseline.
- Narrow-strip stacking is provisional.
- The 580px threshold cannot be driven by a `--_` variable, because native CSS
  variables cannot be used in query conditions.
- Proposals outside the button contract stayed open: a shared --border-subtle
  if the flight border is adopted for other surfaces, a neutral --font-mono
  alias, and the dialog’s maximum width, to be confirmed in a dialog study.
